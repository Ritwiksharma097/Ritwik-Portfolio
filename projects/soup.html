What it is

Soup is the platform underneath a Project Zomboid multiplayer community. It runs across three completely different surfaces (a Lua-modded game server, a Python Discord bot and API, and a Next.js web app) and presents a single, consistent world to its members. A shop you see on the website is the same shop you walk up to in-game. A reputation score generated by an LLM is visible in Discord, on the leaderboard page, and on your in-game character profile.

This season (launched 10 October 2026, after a public beta from 21 September) 399 player accounts have reached the game, on a server with 24 slots. The platform handles their economy, their progression, their shop network, their seasonal events, their leaderboards, and their interactions with Zombita, the AI administrator who works across all three surfaces.

The Zombita interaction page on the Soup website. The same agent appears in Discord and in-game.

The hard part

The technical challenge isn't building a Discord bot, or a game server mod, or a web app. Each of those is a known problem. The hard part is keeping all three in sync as a single system: same source of truth, same state, same identity layer, same economy, same reputation, with users interacting from any surface at any time.

  • Three runtimes, one state. Lua running inside Project Zomboid's Java VM, a Python Discord bot with a FastAPI backend, and a Next.js web app on Cloudflare, none of which natively share memory, schemas, or even basic data types.
  • Real-time bridging. A player buying an item in-game updates the web leaderboard, fires a Discord notification, and decrements the treasury (all within the time it takes to close a dialog box).
  • Identity unification. The same person is a Steam ID in-game, a Discord snowflake in chat, and a session token on the web. Linking those is the prerequisite for everything else.
  • Operability. A community lives or dies on whether its admin can fix things at 2 AM. Soup ships with a full admin layer (RCON from the web, restartable services, in-game item granting, three tiers of server wipe) so an admin can intervene from anywhere.

Architecture

The shape is a hub-and-spoke: a single canonical backend, with three runtime adapters that translate that backend's state into something each surface understands.

                  │   Soup Backend (canonical) │
                  │   Database · Identity ·    │
                  │   Economy · Reputation     │
                  └─────────────┬──────────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
        ▼                       ▼                       ▼
┌───────────────┐       ┌───────────────┐       ┌───────────────┐
│  Lua adapter  │       │  Discord bot  │       │  Web (Next.js)│
│  in-game UI   │       │  Python       │       │  React + SSR  │
│  shopkeeper   │       │  commands +   │       │  shop, leader │
│  dialogs,     │       │  Zombita      │       │  -board, mods │
│  triggers     │       │  conversation │       │  pages, admin │
└───────────────┘       └───────────────┘       └───────────────┘
        │                       │                       │
        └───── Real-time bridge ─────────────────────────┘
                  (single source of truth)

The key design choice: the runtimes never talk to each other. They talk to the backend. This keeps the system from collapsing into N-to-N integration hell, and lets me add a fourth surface (WhatsApp, Teams, a mobile app) without rewiring anything.

The shop network

The clearest demonstration of cross-runtime sync is the shop system. Named shopkeepers run shops with rotating stock and their own wallets. Stock can be edited from the admin panel, viewed publicly on the website, and bought from in-game.

Economy & treasury

The economy is fully closed-loop. Money is finite and tied to real players. A pricing pass runs every six hours within set bands, the treasury only refills after three lean in-game months, part of any money that sits above the cap for three months is burned, and wealth is taxed weekly. Zombita's mood decides where she lands inside those walls. Every transaction (buy, sell, marketplace listing, leaderboard payout) is logged with a full event log going back weeks.

Treasury overview, circulating supply, cycle status, 24h flows.
Per-item inventory. Stock, base prices, dynamic pricing, on/off toggle per item.

The economy isn't just numbers, it's the underlying mechanic that drives player engagement. A poorly-tuned economy kills a community in weeks. Soup's economy has run live since the beta, and every change to it is logged.

Reputation & Zombita's read

Every night Zombita writes a read of each active player, in her own voice, built from what they actually did and said. It's not a stock template. Combined with point totals and an archetype label (competitor / lurker / known / neutral), it doubles as a public-facing social barometer.

The admin workspace

My admins plan and run the server in a workspace I built into the site, which works like Google Docs and Sheets. It has four kinds of document: rich-text docs, spreadsheets, kanban boards, and the server's own config files. Everything syncs live through my own WebSocket relay on Yjs, so when two admins edit the same page they see each other's cursors and changes as they type. Every document keeps a change log and versions that can be rolled back.

The config editor is the careful one. The live copy of servertest.ini or SandboxVars.lua is only a draft. Nothing touches the real file until an admin saves, the backend checks the syntax, and only then writes it, so a broken merge can never reach the running server.

Safehouse tickets

Players grow their safehouses through a ticket. Zombita opens a private Discord channel with a link to the player's own map page, where they drag the edges of their safehouse box out on the live 3D map and see the tile count and the price change as they drag. The page enforces the rules: a new tile next to the old boundary costs 2 bronze, each row further out costs 1 more per tile, the biggest safehouse is 59 x 49, and it can never touch another safehouse.

When the player sends it, a card lands in the channel with Approve, Edit price and Send back. Nothing leaves the player's wallet until an admin approves, and a sent-back drawing comes with the admin's note so the player can redraw. The same page turns a safehouse into a faction safehouse, which needs both the owner and the faction's leaders to agree before an admin approves it.

A ticket on the map page. The dashed box is the player's drawing, 39 x 45 for 6 silver 669 bronze. An admin sent it back with a note to expand inside the fence first. Names and coordinates are blurred.
The same ticket in Discord. The card shows the new tiles and the price, and the admin decides. When it was sent back, Zombita told the player and confirmed nothing was charged.

Faction channels

When players form a faction in game, Zombita opens a private Discord channel and voice room for it and keeps the door: whoever joins or leaves the faction in game is added to or removed from the channel, and she posts each new member and who recruited them. Every faction also gets its own page on the site to set a logo and banner, and the logo shows on the in-game F8 board too.

A faction's channel from its first day. Zombita welcomes them, links their page, opens their voice room and posts each recruit. Player names and the page link are blurred.

Performance from the outside

The Perf page reads the server from files outside the game, so it keeps working when the game is struggling. It shows ticks a minute against the 500 the game needs to keep up, what is loaded (zombies, cars, animals, and zombies near players), the box's load, memory and CPU heat, and the Lua handlers that cost the most time in the last minute, from my own profiler that wraps every mod's event handlers. Its Changes tab shows what changed in the mod list or server settings, before and after, so a slow evening can be traced back to its cause.

The game side

The server runs my own multiplayer mod, now v1.8.180 with 870 Lua files and an admin panel with 52 module switches, updated on a live server with versioned changelogs.

  • Zombita's Jobs. A live job board that rolls tiers D to S from 40+ job types and places each job at one of 182 named spots checked against the map. Jobs can roll a twist or turn out to be a trap, and fights scale with the crew.
  • In-game phone. Six phone models with messages, a wallet, map pins, music that draws zombies on speaker, and games including a true-scale Space Impact remake and chess with Elo. Phone chat runs both ways with Discord.
  • Treasure hunt. Teams follow calls and clues across the map, and each player's in-game phone shows a QR code that opens puzzles on their real phone. The QR encoder is written in Kahlua, which has no bit operators.
  • Job cards. Players take on roles as the server's Mechanic, Medic or Electrician, with their own orders, crafting and clinics. A card lasts five real days, and you can buy one, queue for it, or earn it by doing that work, with ranks from Apprentice to Master.
  • Events and more. Dawn of the Dead horde nights, boss zombies, notoriety and bounties, bus travel between 23 stations, and a live 2D/3D web map.

Engine work

Running all this live means knowing the engine. I traced a vanilla Build 42 crash (a null slot in hen hutch packets on chunk unload) into the 42.21 jar and shipped a guard. I found that command strings over 32 KB crash every client. I wrote an event profiler that wraps every handler across all mods, which found an 83 s freeze and a 148 s blocking call in third-party mods; fixes went to their authors. And I worked out what stops a mod being removed from a live Build 42 save, and built a fix, proven on test servers.

15+ public mods for Build 42, among them Zombita Raft (rafts and boats with a movement model written from scratch), Zombita RV Living and its KI5 add-on, Zombita Bows (an Archery skill with 146 hand-made animation files), Zombita Bikes (pedal bicycles with our own models and riding animations), and Zombita Guns, Melee Weapons and Vehicle Armor.

Zombita NPC System

My newest work, in testing with my server's admins since November 2026. Survivor NPCs with personalities, needs and routines, who learn skills from what they do, pass gossip about you from house to house, keep homes and diaries, and drive with the same motion code on the server and every client. An optional LLM brain can only send intents that the Lua side checks and may refuse. A public Workshop release is planned.

What this project demonstrates

  • Distributed-systems thinking. Hub-and-spoke architecture across three runtimes with real-time state sync.
  • Full-stack ownership. Backend, three frontends, deployment, ops, admin tooling: all solo.
  • Production discipline. Live users, a real economy, operational tooling, and an offline harness that runs mod Lua against fake Java objects before anything ships.
  • Game systems integration. Modding Project Zomboid deeply enough to read the game jar, trace engine crashes and profile every mod on the server.
  • Product taste. The aesthetic, the writing voice, the in-character framing: all part of what makes the community stick.
